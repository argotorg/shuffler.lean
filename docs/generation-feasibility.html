01The actual machine limits

DUP16 reads 16 slots.
SWAP16 moves within 17 slots.

Lists are written bottom first. The last list element is the top. The diagrams draw the top above the bottom.

The names look similar, but their limits differ by one slot. DUP16 copies the value at depth 15. SWAP16 exchanges the top value with the value at depth 16.

The top itself is depth 0. Thus DUP has 16 possible sources, while swaps can move any of the top 17 slots.

A SWAP adds no value and removes no value. It moves two existing occurrences. Repeated swaps with the top can put the entire 17-slot region in any order.

One append moves the bottom of that region out of reach. A value at depth 16 moves to depth 17. No later SWAP can reach that position while the stack only grows.

02Question 2 · generate with swaps

The extra slot helps.
It does not give 17 copying sources.

Allow SWAP, DUP, PUSH, and LOAD. Require exactly the missing additions, in any order. Exclude POP and extra temporary additions. For this question, the final order is unrestricted.

Call a missing value copy-dependent if it can be neither pushed nor loaded. Let K be the set of distinct copy-dependent values in the missing list.

Every kind in K occurs in the initial top 17.And |K| ≤ 16.Necessary and sufficient for generation with swaps under these rules. Proved in Lean by WithSwaps.canGenerate_iff_ready.

Count kinds, not requests.

A request for forty copies of a contributes one kind. A request for one copy of each of seventeen distinct variables contributes seventeen kinds.

Free literals, wildcards, and spilled variables contribute no copying sources to K.

Keep a source inside the next window.

Choose one existing copy of each needed kind. At most 16 such copies fit inside DUP reach.

Use swaps to put them there. Then the proved append-only construction can finish all generation.

If a needed kind is absent from the initial movable region, swaps cannot recover it from deeper positions. Appends only make those deeper positions less accessible.

The Lean proof follows from the exact reserve theorem. With at most 16 needed sources in a 17-slot region, one occurrence remains for the next fixed output. Since the final order is free, choose that occurrence as the output reservation. The reserve theorem supplies an actual trace with no POP and exactly the requested additions.

The proof also covers empty demand and sources shorter than 17 slots. The focused Lean tests check depth 16 versus 17, sixteen versus seventeen kinds, spills, empty sources, repeated requests, and an explicit SWAP16; DUP1 trace.

This does not reserve the correct final bottom value. For generation alone, any expendable bottom slot will do. For exact placement, that slot must contain the next required target value. That extra requirement is the reserve condition below.

03Question 3 · reach the exact final stack

The complete reserve predicate.

Now require the final stack to equal a specified list T. This is a stronger question than generating a multiset of missing values.

Let S be the initial stack, and let H be exactly the values that may be added, with their multiplicities. Swaps may occur between additions. POP and extra additions remain excluded.

The condition has three clauses. All of them inspect the initial data. None runs BBU, chooses a schedule, or updates a shadow stack.

Equal-valued source occurrences may be assigned to target positions freely. A supplied BBU mapping can impose different restrictions on a particular run.

NECESSITY AND SUFFICIENCY PROVED IN LEAN
canPlace_iff_reserve proves both directions using actual production traces.

First, identify the part that can move.

n = length(S)f = max(0, n − 17)W = S.drop(f)The first f slots are already frozen. W is the initial top 17 slots, or the whole source if it is shorter.

List indices count from the bottom. Position f is the bottom of the movable region, not the bottom of the final target's top 17 slots.

Seeds: one source per needed kind.

Seeds contains one occurrence of every distinct copy-dependent value in H.

If H = [a, a, b, 0], and only a and b need copies, then Seeds = [a, b].

The repeated request for a does not require two seeds. The literal 0 does not need a seed.

B: the next output reservation.

If growth is needed and n ≥ 17, define B = [T[f]].

That one occurrence must occupy position f before the first append. The append then makes this position unreachable.

Otherwise, define B = []. The empty and small cases are explained below.

multiset(T) = multiset(S) + multiset(H)and T.take(f) = S.take(f)and B + Seeds ≤ multiset(W)A plan to the exact target exists if and only if all three clauses hold, under the stated operation rules. This is the proved theorem CanPlace ↔ Reserve.
  1. The counts match. The final values are exactly the original values plus the allowed additions.
  2. The part that cannot move is correct. Every initially frozen bottom position already has its required target value.
  3. The working region can do both jobs. It supplies the next fixed output and retains every needed DUP source.

For example, S = [a], H = [a], and T = [a, a, a] fail the count clause. The original stack and permitted additions contain only two copies of a.

+ adds multiplicities. ≤ compares the count of each value. This is more precise than checking only how many slots are available.

In the Lean definition, CanPlace spills S T H means there is an actual Trace from S to T, with trace.noPop and trace.additions = H. The additions count the values actually made by DUP, PUSH, and LOAD.

04The reserve limit is per value

Count the copies of each value.

Suppose the next target value is a, and some missing a still needs DUP. Then B = [a] and Seeds = [a].

B + Seeds = [a, a]Two required occurrences of a. One for output, one to keep copying.

A 17-slot region can have plenty of other values and still fail this check. Its total size is not enough: it must contain two copies of a.

05Why the three clauses are exact

The first growth fixes one position.
Prepare that position first.

First suppose n ≥ 17 and H is nonempty. The first append then freezes a position. Both directions below are proved in Lean.

Why every successful plan needs them

  1. Swaps preserve counts. Each append adds one value. With no POP, the multiset balance is forced.
  2. The first f positions start below SWAP reach. They stay there, so they must already match the target.
  3. Before the first append, only swaps have occurred. The value placed at position f must be T[f], because that append freezes it.
  4. The reserved slot is at depth 16. DUP cannot read it. Each missing copy-dependent kind needs a separate source in the other 16 slots.

This direction is CanPlace.reserve.

How to prepare a plan

  1. Use swaps to put the reserved target value at position f. Keep one source for each needed kind above it.
  2. The prefix through position f is now correct. Exactly 16 current slots remain above that prefix.
  3. The target tail has exactly those working values plus the missing additions.
  4. Fill that target tail one position at a time, using the two cases below.

Reserve.prepare builds this preparation trace. The proof uses actual SWAP operations.

Keep three facts while completing the target.

The fixed prefix is correct. There are at most 16 working slots above it. Those working slots retain one source for every kind that still needs DUP.

Let y be the next target value. Read the cases below as instructions for extending the fixed prefix by one slot.

Case 1: y is still missing.

  1. Generate y. Use PUSH or LOAD if it is free; otherwise use its retained DUP source.
  2. There are now at most 17 working slots. Swaps put the new y next to the fixed prefix.
  3. Keep the previous working values above it. Every remaining needed kind still has its source.
  4. Remove one y from the missing multiset.

Case 2: y is not missing.

  1. The count balance guarantees an existing y in the working slots.
  2. Swaps put one such occurrence next to the fixed prefix.
  3. Remove that occurrence from the working region. No needed source is lost: y is not among the values still to be generated.
  4. The missing multiset stays the same.

In both cases, one more target position is complete. Repeat for the shorter target tail. When the tail is empty, count balance says that the working slots and missing multiset are also empty.

The predicate does not run this construction. The three initial checks contain no recursion. The proof uses a recursive construction to show that those checks imply a plan exists.

The completion theorem is canPlace_complete. It constructs a trace directly, with no POP and exactly the required additions. For a source of at most 16 slots, it starts with an empty fixed prefix. With no additions, a permutation of the movable suffix is enough. Reserve.canPlace joins these cases.

The prefix check is independent. If an initial bottom slot is already below SWAP reach and has the wrong value, enough seeds cannot repair it. Without POP, that position never becomes movable.

Exact values and wildcard patterns are separate inputs.

The core predicate uses exact Value equality. Its T is one concrete result stack. If the target is a wildcard pattern P, a separate proved theorem says:

Some no-POP trace from S has a result matching P↔There exist E and H such thatStackMatches E P and Reserve(spills, S, E, H)

StackMatches requires equal lengths. A wildcard pattern slot accepts any actual value; a concrete pattern slot requires that exact value. This condition chooses both the concrete result E and its exact additions H.

For example, source [a] already matches pattern [*]. Use E = [a] and no additions. Requiring exact equality with the list [Wildcard] would ask a different question.

The pattern theorem is exists_matching_trace_iff_reserve.

How expectedStack fits

For a valid BBU state, use S = state.stack, H = state.missingValues, and T = state.expectedStack. Here S is the current stack. A bound wildcard slot retains its assigned source value in expectedStack.

With a compatible mapping, expectedStack is one matching result. Compatibility means each bound source value matches its target slot, including wildcard slots. This fact is proved by expectedStack_matches.

Reserve for that chosen result is sufficient for a matching plan. Failure for that chosen E and H does not rule out a plan for another matching result. The reserve theorem permits a new assignment of equal-valued occurrences; it does not require preserving BBU's supplied mapping or hole positions.

    08 Why placement stays separate

    Sometimes, a value must be placed
    before generation is finished.

    Generation grows the stack. As it grows, the lower boundary of the SWAP region moves up too. A slot that still needs to move can become too deep.

    This example uses the actual machine limits: DUP reads 16 slots, and SWAP reaches depth 16. It starts with sixteen literal zeros.

    Source: [0, 0, …, 0]  ·  16 zerosMissing: [1, 2]Target: [1, 0, 0, …, 0, 2]The target has 18 slots: a bottom 1, sixteen zeros, and a top 2.

    Ready is true. Both missing literals can be pushed. There is no difficulty in generating them.

    Why the separate phases fail

    At length 16, the original bottom zero is at depth 15. After two appends, it is at depth 17.

    SWAP16 reaches depth 16, not 17. Once both new values have been added, the wrong bottom value is fixed.

    Reversing the generation order cannot help: the original bottom slot still holds zero.

    Permuting the source before generation cannot help either. All sixteen original values are zero.

    So “permute first, generate everything, permute last” is not a complete method under these rules. A placement between the two additions is needed.

    Place 1 while the bottom is still reachable.

    The trace is PUSH 1; SWAP16; PUSH 2. Its production Trace type has been checked in Lean. A valid BBU input with an exact value mapping also returns this target in a checked example.

    The grouped zero blocks above abbreviate several separate slots. Their depth ranges show the exact positions. These diagrams use the actual limits, not a smaller teaching machine.

    A proved consequence of the reserve theorem

    Even initial reach and room to swap are not enough.

    Let a, b1, …, b16 be 17 distinct variables. None is spilled.

    Source: [b1, …, b16, a]Missing: [a]Target: [a, b1, …, b16, a]

    Ready is true: the missing a has a copy at the top. Every initial slot is also within SWAP reach.

    But the only append grows the stack from 17 to 18 slots. It fixes the original bottom position below SWAP reach.

    For that position to match the target, it must contain a before the append. The only a would then be at depth 16, outside DUP reach.

    Copying a while some b is at the bottom fixes the wrong bottom value instead. Swaps before the append cannot remove these two cases.

    No plan reaches this target with exactly the missing addition and no POP. This follows from the proved reserve equivalence and is checked in the focused Lean tests. The missing multiset by itself can still be generated.

    Keep the three questions separate

    1. Can the missing values be generated? The proved Ready condition answers this for append-only plans.
    2. Can the final target order be reached? This also requires placement to remain possible.
    3. Does this BBU run succeed? This depends on BBU's specific generation and placement choices.
    09 The link to BuildBottomUp

    Reachable asks exactly this question
    for the unbound target slots.

    A BBU state contains a current stack and a mapping from current slots to target positions. A target position is unbound when the mapping has no source slot assigned to it.

    state.missingValues collects the values at those unbound target positions. Repeated missing positions give repeated entries.

    For every unbound position, BBU's Reachable predicate asks whether its target value is free, spilled, or present within current DUP reach.

    That is exactly Ready for the list of missing values.

    The general theorem needs no BBU mapping. The BBU theorem only uses the mapping to identify which target values are missing.

    CanGenerate(spills, state.stack,  state.missingValues)↔ Reachable(state)Proved in canGenerate_missing_iff_reachable.

    There is no State.Valid premise. This is a fact about the current stack and the values of the unbound target slots. It does not need the size and mapping invariants used in full BBU correctness.

    For the same reason, it does not certify the values at already bound positions. It does not claim that the mapping is correct or that BBU will finish.

    This is not a new name for BBU's exact success condition. The full algorithm also places values and follows its own choices. Its proved condition remains StaticSuccess.

    A plan can exist even when this BBU run fails.

    S = [0 × 16, 1]H = [1]T = [1, 0 × 16, 1]

    The existing 1 supplies the next output reservation. The missing 1 is a literal, so it needs no DUP seed. All reserve clauses pass.

    SWAP16; PUSH 1 reaches the exact target. The swap puts the existing 1 at the bottom before the append freezes that position.

    For the checked initial mapping i ↦ i + 1, target position 0 is the only hole. The current BBU implementation attempts generation first and returns .blocked 1.

    10The proved foundation

    Why one reachable source per kind
    is enough for append-only generation.

    The full placement theorem above constructs a plan directly, one target position at a time. A separate, smaller theorem explains generation without swaps. It is also proved in Lean.

    The following sections give that theorem in detail: the exact predicates, the role of repeated requests, and the schedule that protects the last reachable copy. Here only DUP, PUSH, and LOAD are allowed.

    11 First, the picture

    A stack has a top.
    DUP has a reach limit.

    In the Lean code, a stack is a list written bottom first. The last list element is the top.

    So [a, b, c] has a at the bottom and c at the top. Appending a value puts it at the top.

    Depth counts down from the top. The top has depth 0. The next slot has depth 1.

    DUP16 reads depth 15. The instruction number is one more than the depth. The repository defines MAX_DUP_DEPTH = 15, so DUP can read 16 slots.

    For generation without swaps, the complete stack can be much larger than 16 slots. A needed copy-dependent value must have a copy inside DUP reach.

    One append shifts every old depth.

    When a new value is added at the top, every old slot becomes one level deeper.

    An old value at depth 14 moves to depth 15. DUP can still read it.

    An old value at depth 15 moves to depth 16. DUP can no longer read that slot.

    This moving boundary is the only difficulty in the generation proof.

    The old slots do not change their list positions. Their depths change because the stack becomes longer.

    12 What is allowed

    Three ways to add one value.

    Each operation appends one value. It leaves all existing slots unchanged.

    DUP

    Copy a value from the top 16 slots. The original copy stays where it was.

    A variable that is not spilled usually needs this route.

    PUSH

    Create a value that is freely generated. A literal or wildcard can use this route.

    No existing stack copy is needed.

    LOAD

    Read a variable from the spill set. Add its value at the top.

    The variable can be absent from the stack.

    In this note, free or spilled means “can use PUSH or LOAD.” A copy-dependent value can use neither. It needs DUP.

    For the append-only generation theorem, SWAP and POP are excluded. Extra temporary copies are also excluded. Every append must account for one requested occurrence.

    13 Three names, three questions

    Read the predicate one layer at a time.

    Let S be the initial stack, and let H be the list of missing values. Repeated values in H request repeated copies.

    The spill set says which variables can be loaded. It stays fixed throughout the plan.

    There are three definitions. Only the first one looks at a single value.

    The names are exact names from the Lean code. The plain-language forms below describe the same conditions.

    Layer 1 · one value

    Available(spills, S, v)

    At least one of three facts holds:

    1. v can be freely generated.
    2. v is a spilled variable.
    3. Some copy of v in S is at depth 0 through 15.

    Intuition: there is a legal way to append this value now.

    Layer 2 · every requested value

    Ready(spills, S, H)

    For every value in H, Available holds on the same initial stack S.

    Intuition: no requested kind is missing its initial source.

    This check does not simulate a run. It does not update a shadow stack. It does not select an order.

    Layer 3 · a complete plan

    CanGenerate(spills, S, H)

    There is an added list A with exactly the same values and counts as H. There is an actual allowed trace from S to S ++ A.

    Intuition: some order of the requested additions works all the way to the end.

    The Lean definition uses A.Perm H for “same values and counts.” It uses trace.onlyGenerates to allow only DUP, PUSH, and LOAD.

    CanGenerate(spills, S, H)↔ Ready(spills, S, H)The arrow works both ways. “A plan exists” and “the initial check passes” are equivalent.

    This is the nonrecursive initial condition. Check the initial top 16 slots and the PUSH/LOAD facts. The theorem handles the later changes in reach.

    14 Counts are fixed; order is free

    Two copies means two copies.

    Suppose the missing list is [a, a, b]. We must add two a values and one b value. We may add them as [a, b, a].

    One source can supply many copies.

    Ready does not need two initial copies of a. One reachable copy can be enough for two, forty, or any finite number of requested copies.

    The schedule keeps a copy reachable for as long as it is needed.

    No extra slots are hidden in the result.

    Adding [a, a, a, b] would not satisfy the request. It adds one extra a.

    Adding only [a, b] would also fail. It omits one requested occurrence.

    Wildcards use exact value equality here. A missing * requests the Value.Wildcard value, which can be pushed. It does not let this theorem replace a requested variable with an arbitrary value.

    15 Why the condition is necessary

    A buried value cannot become exposed.

    Take a requested value x that cannot be pushed or loaded. Its first new copy must come from DUP.

    Before that first copy, the plan has added no new x. The only possible sources are original copies. Each original copy has stayed at its list position and has become no closer to the top.

    If every copy started outside DUP reach, the first DUP of x is impossible.

    This is why CanGenerate implies Ready. A successful plan cannot create a copy-dependent kind that lacks an initial reachable source.

    The Lean proof tracks where each generated value can originate. See CanGenerate.ready.

    16 Why the condition is sufficient

    Protect the last reachable copy.

    Passing the initial check does not make every generation order safe. A plan must preserve one fact after every step:

    Every remaining copy-dependent valuestill has a copy within DUP reach.This is the invariant: the fact we keep true as the stack grows.

    Only one old slot leaves DUP reach during an append: the slot at the bottom of the DUP region. That slot matters only if it is the last reachable copy of a value that is still needed and cannot be pushed or loaded.

    The safe choice at each step

    If the next append would bury a last needed copy, duplicate that value first. Otherwise, add any remaining value.

    The protective duplicate fulfils one real demand. It is not an extra temporary copy.

    1. There is at most one endangered kind. Only one slot crosses the boundary on the next append.
    2. Copying it repairs its own reach. Its new copy is now at depth 0. If more copies are needed, they have a source.
    3. Every other needed kind stays available. It either has a higher copy, or it can be pushed or loaded.
    4. The request gets smaller. Each step removes exactly one occurrence from the missing list. After exactly H.length appends, nothing remains.

    This proves that Ready implies CanGenerate. The Lean construction uses this last-copy rule. See Ready.canGenerate.

    What does “last reachable copy” mean?

    A value may have several copies. Look at the copy nearest the top. If that copy is at depth 15, every other copy is at least as deep. The next append would put all of them outside DUP reach. If the nearest copy is at depth 14 or less, one append cannot lose them all.

    In the small drawings, replace 15 by D − 1, where D is the selected number of readable slots. The real theorem uses D = 16.

      18 An order can fail

      “Some order works” is the exact promise.

      Here x is a variable that is not spilled. The missing values are [0, x]. Both values are available initially.

      Nothing in Ready records an order. The theorem says that at least one valid order exists. A fixed order needs its own check.

      19 What success gives you

      With append-only generation,
      the old stack stays intact.

      The final stack is S ++ A. This is a precise shape, not just a statement about counts.

      Every original slot has its original value at its original list position. All new slots come after that original prefix.

      Any prefix that had to stay fixed therefore stays fixed automatically.

      No bound is required on the initial stack length. No bound is required on the finite missing list length. The source condition is about the needed kinds and their locations.

      Read the result
      S ++ Aunchanged original stack ++ exact requested additions

      “Same position” means the same bottom-first list index.

      It does not mean the same depth. The new top makes all original values deeper.

      The new values can be in any order whose counts match H.

      Read the theorem in one sentence

      One initially reachable source per needed copy-dependent kind is enough, if we can choose the generation order.

      The schedule protects that source until its demand is complete. Exact final placement also requires the output reservation, count balance, and correct frozen prefix explained above.
